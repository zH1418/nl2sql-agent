# 评测与量测（Evaluation）

> 本目录存放 NL2SQL 链路（`create_agent` 探针闭环）的批量量测结果：
> 分层问题集（分组聚合 / TopN 排序 / 多值筛选 / 多表关联）× 参考 SQL 执行结果比对。

## 为什么要有这个目录

单次「跑通了」不能作为证据。**可复现的确定性计数**才是 —— 本目录同时服务三个用途：

| 用途 | 取用方式 |
|---|---|
| **执行结果比对** | `records[].question` + `generated_sql` + `rows` 与 `reference_sql` + `reference_rows` 做**结果比对**（不是比 SQL 文本） |
| **量化分析** | `aggregate` 里的确定性计数（工具调用次数、模型调用次数、预算消耗、召回规模、时延） |
| **回归基线** | 改动后重跑，与 `aggregate` 逐项对比 |

## 文件

| 文件 | 说明 |
|---|---|
| `run_matrix_<日期>.json` | 机器可读：`meta` / `aggregate` / `failure_ledger` / `records[]`（含逐题 SQL、结果行、每次工具尝试） |
| `run_matrix_<日期>.md` | 人读报告：汇总表 + 逐题明细 + 归因分布 |

## 量测暴露的三个真实缺陷（均已修）

### 1. `AOV` 指标的元数据指错列（数据缺陷）

`meta_config.yaml` 里 `AOV.relevant_columns = [fact_order.order_quantity]`，
但 `description` 是「所有订单的**成交金额**平均值」、alias 是「平均订单金额」。

- **后果**：问「各品类的平均订单金额」时模型按元数据取 `order_quantity` ⇒
  算出「平均件数」（手机数码 **1.0**）而非「平均金额」（**6716.24**），并**反复重试至预算耗尽**
- ★ **元数据有 4 处副本，少改一处就不生效**：① `meta_config.yaml` ② MySQL `metric_info`
  ③ MySQL `column_metric` ④ ★ **Qdrant `metric` collection 的 point payload**（**召回时模型实际读的就是它**）
- **踩坑**：第一次只改了 ①②③ ⇒ q05 **仍然算错** ⇒ **「改了配置/数据库」≠「生效」**

### 2. `where` 无法表达「同一列的多个取值」（能力缺口）

`IN` 虽在运算符白名单里，但 `_sql_literal` 对**列表**会退化成 `str(list)` ⇒ 产出垃圾字面量
⇒ **「华东和华南」这类需求根本表达不出来**，模型只能硬凑成
`WHERE region_name='华东' AND region_name='华南'`（**永假**）。

- **修复**：`app/agent/ast_builder.py` 对 `IN` 特判 —— 右值列表 ⇒ 展开为 `('华东', '华南')`；
  标量 ⇒ 自动包成单元素；空列表 ⇒ 归因 `structure`。
  同步在 `build_and_execute` 的 tool description 里加了规则（禁止用两个 `AND`）
- **验证**：pytest 4 条用例（列表展开 / 标量包裹 / 空列表归因 / 等值不受影响）

> ★ **这两条发现本身就是「离线评测有价值」的证据**：在线链路**全程绿灯**
> （`qualify` 通过、有数据返回），错的是**元数据**与**表达力**，
> 只有「与参考 SQL 做结果比对」才暴露得出来。

### 3. `order_by` 的聚合表达式被当成表名（误报 `backbone`）

模型常把排序键写成 `order_by.column = "SUM(fact_order.order_quantity)"`，
而 `_referenced_tables` 用 `split(".")` 取表前缀 ⇒ 得到伪表名 **`SUM(fact_order`**
⇒ 误报 `backbone`，且错误信息进一步误导为「主键列缺失导致 join 链推导失败」——**把模型带偏**。

- **修复**：① 新增 `_strip_agg()` 剥聚合函数外壳；② `_referenced_tables` **只认已知表**
- **验证**：q09 由「`backbone` 失败」转为**命中**（靠预算内重试自纠，5→2）；pytest 5 条用例

> ★ **共性**：三个缺陷发生时**在线链路全是绿的**（`qualify` 通过、有数据返回、无异常），
> 错的是**元数据 / 表达力 / 表名解析** ⇒ 只有「**与参考 SQL 做执行结果比对**」才暴露得出来。
>
> ★ **验证要比「值」，不要只比「行数」**：`AVG(order_quantity)` 与 `AVG(order_amount)` 都是 6 行。

## 方法论沉淀

| # | 方法论 |
|---|---|
| 1 | **工具的边界 = 模型的决策点**；无决策点的连续动作应合并（4 个候选工具 → 3 个，省一轮 LLM 往返） |
| 2 | **分不清是谁的职责，就不要假装能判**（语义漂移在线不可判定 ⇒ 不加确认轮，改为外显理解 + 离线量化） |
| 3 | **在线链路全绿 ≠ 结果正确**（三个缺陷都在「所有信号都绿」的情况下发生） |
| 4 | **白名单里有某个能力 ≠ 它可用**（要测值形态，不只测名字） |
| 5 | **「改了配置」≠「生效」** —— 要确认「读它的那条路」也改了（元数据 4 处副本） |
| 6 | **验证要比「值」不要只比「行数」**（`AVG(数量)` 与 `AVG(金额)` 都是 6 行） |
